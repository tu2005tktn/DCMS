The updated v2 files change S09 from one-week publication to employee-wide recurring weekday/branch templates with dated exceptions. The revised contract is at the start of `docs/specs/S09-UC03.md`. Migration `20261016151440_RecurringWorkingSchedules` adds immutable `WORKING_SCHEDULE_REVISION` and `WORKING_REVISION_PERIOD` rows. Existing weeks, reservations and appointment tables remain intact. New templates repeat from their effective date; an exception replaces only its date. Later effective templates take precedence over earlier templates; exceptions take precedence over both. An employee-wide revision token starts above all legacy week versions, preventing an old booking token from accidentally matching the first recurring publication. Legacy writes are rejected once the employee uses recurring schedules. Reading legacy hours remains possible; they supply availability only when no new effective publication applies.

Shared public availability, draft preview and transaction booking checks use the same resolver for main and assistant staff. Publication checks all future Confirmed reservations across branches, regardless of the preview range. Both publication systems use transaction lock 90403; recurring updates retain receipt replay and immutable history. An editor needs explicit rights at every current/published branch of the employee. A network retry reuses the request key and can replay an already committed result without a stale preview blocking it. Invalid input and connection/stale failures preserve the draft.

## Integration contract

TV2/TV4 consume `DCMS.Application/Features/Scheduling/Contracts.cs`; web shared HTTP types are `web/src/features/working-schedules/contracts.ts`. Public/mobile catalog is `GET /api/availability/options`; slots are `GET /api/availability`. S11 staff uses its authenticated session for 15–480-minute duration. Public requests require the service's catalog duration and 60-minute lead time. GET neither reserves nor returns attendee data.

TV2 must open a ReadCommitted transaction on the same scoped DcmsDbContext, invoke IAvailabilityService.CheckInTransactionAsync, persist ResourceReservation with its returned fixed resources and UTC start/end, and commit. The transaction lock 90403 also protects schedule publication; all writers of reservations, memberships, chairs and availability blocks must follow that lock. ExcludeReservationId is trusted internal input and must be authorized by TV2 when rescheduling. requestKey/appointment workflow and notifications remain TV2 responsibilities. No live agreement or TV2 implementation has been claimed; the interface and contract are ready for owner review.

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
var slot = await availability.CheckInTransactionAsync(check, ct);
// TV2: create/update the authorized appointment and ResourceReservation using slot.
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

For TV4, ISO local date input and explicit +07:00 slot offsets avoid device timezone conversion errors. Keep the returned schedule versions for final reservation checks. Availability may change before submit; MSG111/25/26/27/28 require a fresh query and user review. One chair and all assigned staff must cover the whole duration; identified attendee conflicts are checked internally at commit across branches. Do not use a phone number as a patient identity.

## Duration input regression

Typing 70 minutes was previously permitted by InputNumber's step control but failed server duration validation with the generic MSG110 schedule message. The editor now validates duration separately, displays an inline field message and the nearest 15-minute values (60/75 for 70), preserves invalid/blank input for correction, and avoids sending invalid preview requests. It does not substitute 30 for a blank value or clamp on blur. Public duration remains fixed by the service catalog. Loading is released after validation failure; correcting to 75 immediately enables successful preview with the same weekly draft.

Verification: all 14 web tests passed, including the 70 → blank → 75 browser recovery and public/staff boundary tests; production build passed with the existing Vite bundle-size warning. Direct requests to the running API returned HTTP 400 for 70 minutes (60 ms) and HTTP 200 for 75 (50 ms), so no server hang was reproduced. Backend behavior and the 15-minute contract are unchanged. The updated local Vite server serves this fix.

## Operational limits

The global transaction lock favors correctness over throughput in this iteration. Chair fixture hours are daily; chair-specific occupancy is represented in the reservation seam. Branch/service/staff administration, appointment commands/S12, reservation notifications, recurring booking and mobile screen implementation remain with their feature owners. No appointment or patient record is created by reading availability or publishing a work week.
