# Database design reference

The current EF Core relational model contains 32 application tables (33 physical base tables in `public` including `__EFMigrationsHistory`, totaling 439 columns — 437 domain columns — after simplifying the remaining 9 multi-column tables from 198 to 121 columns on 18 November 2026, see [remaining nine tables simplification](../specs/REMAINING-NINE-TABLES-SIMPLIFICATION.vi.md), and the remaining 8 small domain tables from 90 to 61 columns, see [remaining eight small tables simplification](../specs/REMAINING-EIGHT-SMALL-TABLES-SIMPLIFICATION.vi.md)). Its executable definition is the checked-in migrations and `DcmsDbContextModelSnapshot`. The initial consolidation replaced 40 source tables with three shared stores and embedded seven collections in their parent records. Later steps consolidated accounts, scheduling, examinations, treatment, patient care, lab orders, settings catalogs and notifications, removed the finance module until it is specified again, and simplified individual high-column tables. See [the storage contract](../specs/DATABASE-SIMPLIFICATION.vi.md) for migration, JSONB collections and API behavior.

`DCMS_Logical_ERD_37_Tables.mmd` preserves the original logical design supplied on 6 October 2026. Use the current feature specifications and EF model to review the implemented physical schema.

Account and authorization storage uses exactly two tables: `USER_ACCOUNT` (18 physical columns plus PostgreSQL hidden `xmin` row-version concurrency token; JSONB `AuthData` holds security flags, claims, logins, tokens, sessions, email verifications and recovery state) and `ACCESS_GROUP` (10 columns: functional unique indexes enforce `UPPER("Code")` and `UPPER("Name")` per `RecordKind`; `Version` replaces `RoleConcurrencyStamp`, and Identity role claims share the `Grants` JSONB column). Functional unique indexes enforce uppercase username, uppercase email and normalized phone uniqueness; `EmployeeProfile` shares `FullName` and `StaffAccessAssignment` shares `Version` with `ApplicationUser`. Clinical foreign keys retain the historical `EmployeeId`. See [the account storage contract](../specs/ACCOUNT-TWO-TABLES.vi.md) and [the current table inventory](DATABASE-TABLE-INVENTORY.vi.md). See [implementation decisions](../implementation/UC01-UC31.md). Preserve remaining composite/conditional keys and transactional rules when implementing later features; Mermaid annotations alone do not enforce them.

Scheduling storage uses `SCHEDULING_BRANCH` (11 columns: contact info, `SlotIntervalMinutes`, `Version`, and `Members`/`Chairs` as JSONB, without table-splitting `BranchProfile` or logo/bank/website/timezone fields; see [SCHEDULING_BRANCH simplification](../specs/SCHEDULING-BRANCH-TABLE-SIMPLIFICATION.vi.md)), `WORKING_SCHEDULE` (weeks and recurring revisions), and `APPOINTMENT` (22 columns without a separate `ResourceReservation` entity, using `Version` as its concurrency token and storing booking declaration metadata in `BookingInfo`, support requests in `SupportRequests`, and reminders in `Reminders` as JSONB; see [APPOINTMENT simplification](../specs/APPOINTMENT-TABLE-SIMPLIFICATION.vi.md)). Treatment services remain in the shared `SCHEDULING_SERVICE` catalog (10 columns: drops unused `BillingUnit`, `IsInvestigationService`, `InvestigationKind`). Appointment history uses `AUDIT_LOG`; outbox events use the shared notification store. See [the scheduling storage contract](../specs/SCHEDULING-STORAGE-REVIEW.vi.md).

Examination storage uses `VISIT` for attendance, examination content and investigation orders, and `CLINICAL_DOCUMENT` (15 columns: `Metadata` JSONB for source/description/size/sha256/rejectReason/investigationId, `Reviews` JSONB and `AiAnalyses` JSONB; `PlanId` retired) for file metadata and clinical reviews. Legacy clinical source references are archived in the shared audit store with a reversible schema snapshot. See [the examination storage contract](../specs/EXAMINATION-TWO-TABLES.vi.md). Prescriptions use `PRESCRIPTION` (simplified to 11 columns keeping `PatientPrescription` and `Items` JSONB without `ExternalPrescription` or `PrescriptionTemplate` columns) and `CATALOG_MEDICINE` (simplified to 10 columns with `Spec` JSONB and `IX_CATALOG_MEDICINE_Name_Upper`); see [prescription and medicine table simplification](../specs/PRESCRIPTION-AND-MEDICINE-TABLE-SIMPLIFICATION.vi.md).

Treatment storage uses `TREATMENT_DOSSIER` (14 columns, using `Version` as its concurrency token and storing sheet drafts as JSONB without `RevisionDrafts`, `StorageStamp` or redundant plan/closure/deposit fields; see [TREATMENT_DOSSIER simplification](../specs/TREATMENT-DOSSIER-TABLE-SIMPLIFICATION.vi.md)), `TREATMENT_PLAN_ITEM` (18 columns matching the treatment sheet plan grid without `Steps` JSONB, warranty, consent or extended V23 fields; see [TREATMENT_PLAN_ITEM simplification](../specs/TREATMENT-PLAN-ITEM-TABLE-SIMPLIFICATION.vi.md)), `CLINICAL_ACTIVITY` (20 performed-activity columns) and `TREATMENT_TEMPLATE` (8 columns: `Version` concurrency token and `Items` JSONB; drops `DefinitionKind`, `Versions`, `StorageStamp`). Treatment and progression events use `AUDIT_LOG` with their own `EventActorId` column, because system jobs record events with actor 0. See [the treatment storage contract](../specs/TREATMENT-FOUR-TABLES.vi.md).

Patient care uses one table, `CARE_TASK` (11 columns: core task fields, `Version` concurrency token and `ContactAttempts` JSONB; `CareEscalation`, `EpisodeKey`, `StorageStamp` and audit columns retired; `UX_CARE_TASK_MissedAppointment` partial unique index replaces `EpisodeKey`). Lab work uses `LAB_ORDER` (simplified to 18 columns with prosthodontic details & intermediate dates in `Spec` JSONB, status history in `StatusLogs` JSONB, and dossier/patient/branch resolved via `ActivityId -> CLINICAL_ACTIVITY -> TREATMENT_DOSSIER`; see [LAB_ORDER table simplification](../specs/LAB-ORDER-TABLE-SIMPLIFICATION.vi.md)) and the `LAB_WORK_TYPE` catalog (9 columns with `IX_LAB_WORK_TYPE_Name_Upper`). The finance module and its 18 tables were removed on 13 November 2026. See [the care, lab and finance storage contract](../specs/CARE-LAB-FINANCE-STORAGE.vi.md).

Settings and catalogs use `CLINIC_SETTINGS_VERSION` (6 columns), `REFERENCE_ENTRY` (8 columns with `IX_REFERENCE_ENTRY_Kind_Name_Upper`, without `NormalizedName` or `Created*`/`Updated*`), `CATALOG_PROVIDER` (9 columns with `IX_CATALOG_PROVIDER_Name_Upper`), plus material catalogs/logs (`MATERIAL_CATEGORY` 4 cols, `MATERIAL_CATALOG_ITEM` 6 cols, `MATERIAL_PURCHASE` 17 cols, `MATERIAL_USAGE` 6 cols linking `ActivityId` to `CLINICAL_ACTIVITY`). Catalog change history and replay receipts are stored in the shared `COMMAND_RECEIPT` table; the retired `/api/settings` tables are archived in `AUDIT_LOG` with a reversible schema snapshot. See [the settings and catalog storage contract](../specs/SETTINGS-CATALOG-STORAGE.vi.md).

Notifications use one table, `IN_APP_NOTIFICATION` (19 columns with `Data` JSONB holding `RequestId`, `DeepLink`, `HasExternalFailure`, `LastAttemptAt`, `PayloadJson`, `DispatchedAt`; unified `Guid?` `AppointmentId`, `varchar(80)` `Kind`, `CreatedAt`, `Status`, `Error`), whose rows are in-app notifications, appointment outbox events, per-channel delivery attempts and staff handling items, plus `PUSH_DEVICE` (5 columns). Patient and family modules (`PATIENT_PROFILE` 16 columns with `Details` JSONB, `PATIENT_ACCOUNT_LINK` 11 columns with `Details` JSONB, `CUSTOMER_FAMILY_MEMBER` 9 columns without `CreatedAt`/`UpdatedAt`, `FAMILY_RECORD_ACCESS` 13 columns with `Details` JSONB) preserve all four tables. See [the notification storage contract](../specs/NOTIFICATION-STORAGE.vi.md).
