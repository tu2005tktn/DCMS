# Database design reference

The current EF Core relational model contains 31 application tables after the 12-13 November 2026 storage consolidation. Its executable definition is the checked-in migrations and `DcmsDbContextModelSnapshot`. The initial consolidation replaced 40 source tables with three shared stores and embedded seven collections in their parent records. Later steps consolidated accounts, scheduling, examinations, treatment, patient care, lab orders, settings catalogs and notifications, and removed the finance module until it is specified again. See [the storage contract](../specs/DATABASE-SIMPLIFICATION.vi.md) for migration, JSONB collections and API behavior.

`DCMS_Logical_ERD_37_Tables.mmd` preserves the original logical design supplied on 6 October 2026. Use the current feature specifications and EF model to review the implemented physical schema.

Account and authorization storage uses exactly two tables: `USER_ACCOUNT` and `ACCESS_GROUP`. Custom Identity stores preserve password hashing, role/claim/login/token APIs while storing child collections as JSONB. Employee profiles and access assignments share the account row; clinical foreign keys retain the historical employee ID. See [the account storage contract](../specs/ACCOUNT-TWO-TABLES.vi.md) and [the current table inventory](DATABASE-TABLE-INVENTORY.vi.md). See [implementation decisions](../implementation/UC01-UC31.md). Preserve remaining composite/conditional keys and transactional rules when implementing later features; Mermaid annotations alone do not enforce them.

Scheduling storage uses `SCHEDULING_BRANCH` (members, chairs and logo metadata as JSONB), `WORKING_SCHEDULE` (weeks and recurring revisions), and `APPOINTMENT` (booking and resource reservation share a row, with support requests and reminders as JSONB). Treatment services remain in the shared `SCHEDULING_SERVICE` catalog. Appointment history uses `AUDIT_LOG`; outbox events use the shared notification store. See [the scheduling storage contract](../specs/SCHEDULING-STORAGE-REVIEW.vi.md).

Examination storage uses `VISIT` for attendance, examination content and investigation orders, and `CLINICAL_DOCUMENT` for file metadata and clinical reviews. Legacy clinical source references are archived in the shared audit store with a reversible schema snapshot. See [the examination storage contract](../specs/EXAMINATION-TWO-TABLES.vi.md).

Treatment storage uses `TREATMENT_DOSSIER` (sheet and revision drafts as JSONB), `TREATMENT_PLAN_ITEM` (steps as JSONB), `CLINICAL_ACTIVITY` (performed activities, reviews, care notes and follow-up instructions share the table by record kind) and `TREATMENT_TEMPLATE` (items and legacy versions as JSONB). Treatment and progression events use `AUDIT_LOG` with their own `EventActorId` column, because system jobs record events with actor 0. See [the treatment storage contract](../specs/TREATMENT-FOUR-TABLES.vi.md).

Patient care uses one table, `CARE_TASK`, with contact attempts and escalations as JSONB. Lab work uses `LAB_ORDER` (status history as JSONB) and the `LAB_WORK_TYPE` catalog. The finance module (charges, examination fees, invoices, receipts, advances, refunds, receivables, dossier payments, PayOS and revenue) and its 18 tables were removed on 13 November 2026; treatment work still records a fee request event for a future finance consumer. See [the care, lab and finance storage contract](../specs/CARE-LAB-FINANCE-STORAGE.vi.md).

Settings and catalogs use `CLINIC_SETTINGS_VERSION`, `REFERENCE_ENTRY` and `CATALOG_PROVIDER`. Catalog change history and replay receipts are stored in the shared `COMMAND_RECEIPT` table; the retired `/api/settings` tables are archived in `AUDIT_LOG` with a reversible schema snapshot. See [the settings and catalog storage contract](../specs/SETTINGS-CATALOG-STORAGE.vi.md).

Notifications use one table, `IN_APP_NOTIFICATION`, whose rows are in-app notifications, appointment outbox events, per-channel delivery attempts and staff handling items. Deliveries and handling items stay separate rows so retries and read marks do not contend. The development `public` schema has 32 physical tables, including EF migration history. See [the notification storage contract](../specs/NOTIFICATION-STORAGE.vi.md).
