# Database design reference

The current EF Core relational model contains 57 application tables after the 12-13 November 2026 storage consolidation. Its executable definition is the checked-in migrations and `DcmsDbContextModelSnapshot`. The initial consolidation replaced 40 source tables with three shared stores and embedded seven collections in their parent records. Later steps consolidated accounts, scheduling, examinations and treatment. See [the storage contract](../specs/DATABASE-SIMPLIFICATION.vi.md) for migration, JSONB collections and API behavior.

`DCMS_Logical_ERD_37_Tables.mmd` preserves the original logical design supplied on 6 October 2026. Use the current feature specifications and EF model to review the implemented physical schema.

Account and authorization storage uses exactly two tables: `USER_ACCOUNT` and `ACCESS_GROUP`. Custom Identity stores preserve password hashing, role/claim/login/token APIs while storing child collections as JSONB. Employee profiles and access assignments share the account row; clinical foreign keys retain the historical employee ID. See [the account storage contract](../specs/ACCOUNT-TWO-TABLES.vi.md) and [the current table inventory](DATABASE-TABLE-INVENTORY.vi.md). See [implementation decisions](../implementation/UC01-UC31.md). Preserve remaining composite/conditional keys and transactional rules when implementing later features; Mermaid annotations alone do not enforce them.

Scheduling storage uses `SCHEDULING_BRANCH` (members, chairs and logo metadata as JSONB), `WORKING_SCHEDULE` (weeks and recurring revisions), and `APPOINTMENT` (booking and resource reservation share a row, with support requests and reminders as JSONB). Treatment services remain in the shared `SCHEDULING_SERVICE` catalog. Appointment history uses `AUDIT_LOG`; outbox events use the shared notification store. See [the scheduling storage contract](../specs/SCHEDULING-STORAGE-REVIEW.vi.md).

Examination storage uses `VISIT` for attendance, examination content and investigation orders, and `CLINICAL_DOCUMENT` for file metadata and clinical reviews. Legacy clinical source references are archived in the shared audit store with a reversible schema snapshot. See [the examination storage contract](../specs/EXAMINATION-TWO-TABLES.vi.md).

Treatment storage uses `TREATMENT_DOSSIER` (sheet and revision drafts as JSONB), `TREATMENT_PLAN_ITEM` (steps as JSONB), `CLINICAL_ACTIVITY` (performed activities, reviews, care notes and follow-up instructions share the table by record kind) and `TREATMENT_TEMPLATE` (items and legacy versions as JSONB). Treatment and progression events use `AUDIT_LOG` with their own `EventActorId` column, because system jobs record events with actor 0. The development `public` schema has 58 physical tables, including EF migration history. See [the treatment storage contract](../specs/TREATMENT-FOUR-TABLES.vi.md).
