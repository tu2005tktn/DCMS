# DCMS business rules (from code)

Rules actually enforced by the current backend (`backend/src`), mapped to the refined use cases UC-01 to UC-46. Generated 22 November 2026 from the services, domain rules and endpoints; the older v2.5 GBR list in `DCMS_Use_Cases_Business_Rules_Messages_v2.5.docx` contains rules that are no longer, or not yet, implemented.


Field-level limits (length, format, range) are intentionally excluded; they belong to the field specifications.

| GBR-ID | Rule Statement | Applies To | Rationale | Enforced By |
|---|---|---|---|---|
| GBR-001 | **Generic sign-in failure**<br>Sign-in fails with one generic message when the identifier or password is wrong or the account is inactive or locked. Patients sign in with their phone number or registered e-mail; staff with their user name. | UC-01 | Do not reveal whether an account exists or why it cannot be used. | System authentication |
| GBR-002 | **Session lifetime and renewal**<br>An access token lasts 15 minutes and a refresh token 30 days (configurable 1-60 minutes / 1-365 days). Every renewal rotates the refresh token; reusing an old refresh token revokes the whole session. Sign-out revokes the session. | UC-01 | Limit the damage of a stolen token and end sessions reliably. | System token service |
| GBR-003 | **Staff idle sign-out**<br>A staff web session ends automatically when there is no interactive activity for the configured idle time (5, 10, 20, 30, 60, 90 or 120 minutes; default 20). Patient sessions are not affected. | UC-01, UC-44 | Protect patient data on shared clinic computers. | Clinic Owner configuration; system session check |
| GBR-004 | **Locked or inactive accounts**<br>A locked or inactive account cannot sign in, renew a session or perform any action. Locking an account revokes all of its active sessions immediately. | UC-01, UC-05 | Removed access must take effect at once. | Admin; system session check |
| GBR-005 | **Google sign-in**<br>Google sign-in works only when it is configured on the server and the Google token is valid with a verified e-mail. It is limited to patient accounts; if the e-mail already belongs to an account not linked to Google, the sign-in is refused. | UC-02 | Prevent taking over an existing account through a Google e-mail. | System Google token verification |
| GBR-006 | **Recovery code limits**<br>A recovery code (6 digits by default) is valid for 15 minutes and is sent only to a verified contact (or the registered e-mail of a patient). A new code invalidates older unused codes. At most 5 verification attempts, a resend after 2 minutes and at most 3 resends; at most 5 requests per account and 20 per IP address per hour. | UC-04 | Resist guessing and abuse of the recovery channel. | System recovery service |
| GBR-007 | **Neutral recovery answer**<br>A recovery request always returns the same neutral message whether or not the account exists. | UC-04 | Do not let the form be used to discover accounts. | System recovery service |
| GBR-008 | **Effects of a password reset**<br>A successful reset revokes all sessions of the account and does not unlock a locked account. An Admin may start the recovery for a staff account. Every reset is recorded in the account history. | UC-04, UC-05 | Old sessions must not survive a credential change. | System recovery service; Admin |
| GBR-009 | **Staff account identity**<br>Only an Admin (or a member of a group with account grants) manages staff accounts. User name, e-mail, phone number and employee code must be unique; full name is required (max 160). | UC-05 | Each staff member has exactly one identifiable account. | Admin; system uniqueness check |
| GBR-010 | **Lock and unlock history**<br>Locking or unlocking a staff account requires a reason (max 500). Every account change is kept in the change history with actor, time and before/after values. | UC-05 | Accountability for access changes. | Admin; system audit |
| GBR-011 | **Access group grants**<br>An access group has a base role (Admin, Dentist or Clinic Assistant) and a list of valid, non-duplicated screen and action grants. A child grant requires its parent grant. A non-Owner can only give grants they hold. Group code and name are unique. | UC-06 | Nobody can grant more than they own; grants stay consistent. | Clinic Owner, Admin; system grant validation |
| GBR-012 | **Access group protection**<br>A group that still has staff assigned cannot be deactivated or change its base role. A user cannot change an assignment that includes themselves; a non-Owner can only assign staff within their own branches. Changes need a reason (max 1000). | UC-06 | Avoid self-escalation and orphaned staff access. | Clinic Owner, Admin; system validation |
| GBR-013 | **Branch data scope**<br>Staff see and act only on data of the branches they are assigned to. A dentist without wider grants sees only their own appointments in the calendar. | UC-05, UC-06, UC-15, UC-23, UC-24 | Keep each branch's data within its staff. | System permission check |
| GBR-014 | **Appointment reminders**<br>The system schedules reminders 24 hours and 2 hours before a confirmed appointment; a reminder whose time has already passed is not created. There is one reminder per appointment version, lead time and recipient; a reschedule or cancellation supersedes pending reminders. | UC-07, UC-08, UC-09, UC-17 | Remind patients once, at the right time, for the current appointment. | System notification dispatcher |
| GBR-015 | **Delivery failure**<br>A failed push delivery is retried up to 3 attempts (after 1, 5 and 15 minutes); after that it is marked failed and a staff handling item is created. A delivery failure never undoes the appointment action. | UC-07 | Appointments stay valid even when messaging fails. | System notification dispatcher |
| GBR-016 | **Booking lead time**<br>An online booking must start at least 60 minutes from now. Staff may book closer to the start only with an exception reason (max 500). No appointment can start in the past. | UC-08, UC-16 | Give the clinic time to prepare. | System booking validation |
| GBR-017 | **Online service and duration**<br>Online booking is allowed only for the branch's active initial-examination service that is publicly bookable, using its configured duration; patients cannot enter a duration. Any appointment lasts 1 to 480 minutes. | UC-08, UC-16, UC-22 | Keep booking duration consistent with the service. | Clinic Owner configuration; system validation |
| GBR-018 | **Slot boundaries**<br>Start times are generated from published Work periods stepped by the branch slot interval. The whole appointment must fit inside a Work period without overlapping a Break; slots in the past are never offered. | UC-08, UC-16, UC-17, UC-21 | Keep appointments within available working time. | System slot generation |
| GBR-019 | **Resource conflicts**<br>The same dentist (and assistant) cannot have overlapping appointments, and an identified patient cannot have two overlapping appointments. Each appointment needs a free active chair of the branch. Confirmed, Checked-in and In-progress appointments occupy time. | UC-08, UC-16, UC-17 | Prevent double booking of people and chairs. | System availability check |
| GBR-020 | **Any dentist assignment**<br>When "any dentist" is chosen, each start time shows at most one slot, assigned to the free on-shift dentist with the fewest active bookings that day (ties: lower ID). | UC-08, UC-16 | Spread the workload fairly between dentists. | System slot generation |
| GBR-021 | **Booking for self or a relative**<br>A booking for oneself uses the verified linked patient record. A family member can only be booked by the patient account that owns that (not deleted) member. A patient can only use their own verified patient record. | UC-08, UC-13 | Patients cannot book on someone else's record. | System booking validation |
| GBR-022 | **Automatic confirmation and safe retry**<br>A valid booking is Confirmed immediately; there is no pending approval. Availability and the schedule version are re-checked inside a serialized transaction. Retrying with the same request key returns the same appointment; the same key with different content is rejected. | UC-08, UC-16 | No double booking from concurrent or repeated requests. | System booking transaction |
| GBR-023 | **Self-service change window**<br>A patient can reschedule or cancel their own Confirmed appointment only when at least 12 hours remain (exactly 12 hours qualifies); closer to the start they must send a support request. | UC-09 | Give the clinic enough time to reuse the slot. | System change validation |
| GBR-024 | **Safe rescheduling**<br>The new start must be at least 60 minutes ahead, differ from the current time, dentist or chair, and pass the availability check. If it fails, the original appointment is kept. A reason (max 500) is required and every change is logged with old and new values and the actor. | UC-09, UC-17, UC-20 | A failed change never loses the original booking. | System change validation |
| GBR-025 | **Cancellation**<br>Cancellation requires a reason (max 500) and is recorded with actor and time; the interval becomes free again. Staff can cancel a Confirmed appointment any time before it starts. | UC-09, UC-18 | Keep a traceable history of cancellations. | Patient, Clinic Assistant, Dentist; system |
| GBR-026 | **Support request creation**<br>A support request can be sent only for a Confirmed appointment that has not started, with a reason (max 500). There is at most one pending request per appointment. The patient can withdraw only a Pending request; the appointment stays valid until the clinic handles it. | UC-09, UC-20 | Changes close to the appointment go through the clinic. | System support request validation |
| GBR-027 | **Support request handling**<br>Only Pending requests can be handled. Staff must record how the requester was verified (max 500) before applying a change or cancel; resolving such a request requires the change to have been applied; a rejection requires a reason. | UC-20 | Only verified requesters can change an appointment. | Clinic Assistant; system |
| GBR-028 | **Self link request**<br>Only a patient account can request a link and must confirm the record is their own. One open request at a time (a repeated request returns the existing one); refused if the account already has a verified link. The request can be withdrawn only while Pending. | UC-10 | One account maps to one own patient record. | System link validation |
| GBR-029 | **Link verification**<br>The assistant can approve only when the patient record exists (created at the first check-in), the full name matches and the declared birth date and patient code (if given) match, the account is an active patient account, and neither the account nor the record has another verified self link. A verification note (max 1000) is required; a link can be revoked. | UC-10, UC-25 | Medical data is shown only to the right person. | Clinic Assistant; system matching check |
| GBR-030 | **Own record access**<br>A patient sees their medical record and can update their information only through a verified link; each read is recorded. | UC-11, UC-12 | Protect medical records from unverified accounts. | System permission check |
| GBR-031 | **Own information update**<br>A patient can edit only the administrative fields (name, birth date, gender, phone, address, guardian) of a linked, non-archived record. Internal notes and catalog fields stay unchanged and the required-field policy applies. | UC-12 | Patients keep their contact data current without touching clinical data. | System validation |
| GBR-032 | **Family record access grant**<br>The assistant approves access only with a sharing basis (patient consent or legal representative), at least one valid scope (examinations, treatment, prescriptions, documents) and an expiry in the future within 365 days. The record must be active, belong to the assistant's branch, and match the declared name and birth date. | UC-14, UC-25 | Share a relative's record only with consent and limits. | Clinic Assistant; system validation |
| GBR-033 | **Family record access use**<br>The owner sees only the granted scopes while the access is Verified and not expired. The owner can withdraw a Pending or Verified request; staff can revoke a grant. | UC-14 | Access ends when consent or time ends. | System permission check |
| GBR-034 | **Counter booking rights**<br>Standard and walk-in bookings are made by a Clinic Assistant (or a group with the create-appointment grant) of the branch; a dentist books only a treatment follow-up of their own plan. The source is Phone, Zalo, Facebook, In person or App; walk-in is staff only. | UC-16, UC-19 | Bookings come from the right role and are traceable to a channel. | System permission check |
| GBR-035 | **No-show**<br>Only staff can mark a No-show, only for a Confirmed appointment whose start time has passed and that has not been checked in. A reason is required. Staff may undo a mistaken No-show only on the clinic day it was recorded, with a reason, while no other active appointment overlaps the same chair, dentist or patient and the linked treatment sheet has not been removed. On the same day staff may also move a late or No-show appointment to a free future time without the 60-minute lead time, with a reason, unless the person already holds another open self-booked examination or the treatment sheet has been removed. | UC-18 | Do not overwrite a patient who actually arrived. | Clinic Assistant, Dentist; system |
| GBR-036 | **Walk-in replacement**<br>A walk-in replacement can use only the slot of a No-show appointment that is still running, with the same branch and dentist, ending within that slot, and only if the original appointment has no visit. | UC-18 | Reuse freed chair time without conflicts. | Clinic Assistant; system availability check |
| GBR-037 | **Next visit booking**<br>A next visit needs an open treatment sheet of the same patient and branch and the patient's consent. Candidates come from open plan items and are offered within 4 days before or after the planned date (an overdue item counts from today). | UC-19, UC-31 | Follow-up visits follow the agreed treatment plan. | Clinic Assistant, Dentist; system |
| GBR-038 | **Missed appointment task**<br>Each No-show (with or without a patient record) creates exactly one "missed appointment" care task once the clinic day on which it was recorded is over; reprocessing never creates duplicates. | UC-18, UC-26 | Every missed patient is followed up once. | System care task job |
| GBR-039 | **Care task updates**<br>A care task is Open, In progress, Done or Cancelled; Done or Cancelled tasks cannot change. A contact attempt records the channel (phone, in person, other) and the result (reached, no answer, rebooked, declined, other) with actor and time; next action max 1000. | UC-26 | Keep a reliable history of customer contact. | Clinic Assistant, Dentist; system |
| GBR-040 | **Working periods**<br>Periods use 15-minute steps within the day with start before end, and are Work or Break. A Break needs a reason (max 500) and must lie inside a Work period; periods of the same kind cannot overlap; at most 140 periods per week; the week starts on Monday. | UC-21 | Avoid conflicting published work intervals. | Clinic Owner, Dentist; system schedule validation |
| GBR-041 | **Template and exception**<br>The weekly template applies by weekday; a one-day exception overrides only that date and requires a reason. The slot preview covers at most 31 days. | UC-21 | Handle one-off changes without rewriting the template. | System schedule validation |
| GBR-042 | **Protect confirmed appointments**<br>A schedule change that would leave confirmed appointments outside working time cannot be published until those appointments are handled. | UC-21 | Published bookings are never silently broken. | System impact check |
| GBR-043 | **Check-in eligibility**<br>Only a Confirmed appointment of the current clinic day that has not ended can be checked in; a No-show appointment cannot. | UC-23 | Reception works only on today's valid bookings. | System reception validation |
| GBR-044 | **Identity at check-in**<br>The chosen patient record must match the appointment (its linked patient, or the attendee name and birth date) and must not be archived. One appointment opens one visit; checking in again returns the existing visit. | UC-23 | The right patient is attached to the right visit. | Clinic Assistant; system matching check |
| GBR-045 | **Arrival time**<br>The arrival time cannot be in the future and must be on the same clinic day; recording an earlier time needs a permission and a reason. | UC-23 | Keep the queue times truthful. | System validation |
| GBR-046 | **Required patient fields**<br>Saving a patient enforces the required fields set in general settings (only fields the record has). A newly required field applies from the next save; existing records are not changed or filled automatically. | UC-24, UC-44 | Collect the data the clinic needs. | Clinic Owner configuration; system validation |
| GBR-047 | **Duplicate check**<br>Before creating or editing, the system lists possible duplicates (same normalized name, same phone, or same birth date with the same given name) and the user must confirm they reviewed them. Records are never merged automatically. | UC-23, UC-24 | Avoid duplicate patient records. | Clinic Assistant; system duplicate check |
| GBR-048 | **Patient code**<br>The patient code follows the configured mode (automatic, automatic with manual override, or manual only) and prefix. A manual code must be unique; issued codes never change; the next number can only move forward. | UC-24, UC-44 | Each patient has one stable, unique code. | System code generation |
| GBR-049 | **Archived records**<br>An archived record cannot be edited, checked in or prescribed for until it is restored. | UC-24, UC-23, UC-38 | Inactive records stay read-only. | System validation |
| GBR-050 | **Visit workflow**<br>An examination starts only when the visit is Queued and the appointment Checked-in, and is saved or confirmed while In progress. A visit for treatment continuation cannot be used for an examination. | UC-27 | Keep the visit states consistent. | Dentist; system state check |
| GBR-051 | **Confirm examination**<br>Confirming an examination requires at least one diagnosis and a disposition; inactive diagnosis entries cannot be used. | UC-27, UC-40 | A confirmed examination has a clinical conclusion. | Dentist; system validation |
| GBR-052 | **Complete and hand over**<br>Completing a visit requires the dentist to confirm the work was reviewed and every investigation required for the diagnosis to be Reviewed or Cancelled. Handover to treatment is possible only after a confirmed examination with the disposition "proceed to treatment". | UC-27, UC-31 | No visit closes with unread results. | Dentist; system validation |
| GBR-053 | **Examination amendment**<br>A confirmed or completed examination can only be changed by an amendment with a reason (max 1000); the history is kept. | UC-27 | Clinical records stay traceable. | Dentist; system audit |
| GBR-054 | **Investigation lifecycle**<br>An investigation goes Ordered, Result available, Reviewed, or Cancelled (from Ordered or Result available). It can be ordered only for an open visit; ordering after the examination is confirmed needs a reason. A result needs text or a file; review needs a result. | UC-28 | Results are received and read before decisions. | Dentist, Clinic Assistant; system state check |
| GBR-055 | **File integrity and deletion**<br>Each file is stored with a SHA-256 hash checked on every download. Deleting is a soft delete with a reason (max 500) and audit; files that are investigation results cannot be deleted. | UC-29 | Clinical evidence cannot be altered or lost. | System document service |
| GBR-056 | **AI X-ray analysis**<br>AI analysis runs only when the AI service is configured, on a ready X-ray document in JPEG or PNG, at most 20 times per document. The result is a suggestion kept with the document; if the service fails nothing is saved and the user can retry. | UC-30 | AI supports, but never replaces, the dentist's diagnosis. | Dentist; system AI client |
| GBR-057 | **Open sheet required**<br>Planning, recording work, copying items and lab orders are allowed only while the treatment sheet is Open. | UC-31, UC-32, UC-35 | Closed sheets stay unchanged. | System state check |
| GBR-058 | **Price and discount**<br>Prices are never negative. Line amount = quantity x agreed unit price, rounded. A discount is Fixed (whole VND) or Percent (max 100), never more than the line amount, and a non-zero discount needs a reason. | UC-31, UC-32, UC-40 | Agreed prices and discounts are justified. | Dentist, Clinic Owner; system calculation |
| GBR-059 | **Close treatment sheet**<br>The outcome is Completed as agreed, Completed with revised scope (needs a plan revision) or Stopped incomplete; a reason is required except for Completed as agreed, which needs an agreed plan. Upcoming follow-up appointments of the sheet must be handled first. | UC-33 | A sheet closes with a clear outcome. | Dentist, Clinic Owner; system validation |
| GBR-060 | **Reopen treatment sheet**<br>Only a Completed or Stopped sheet can be reopened, with a reason (1-1000). A cancelled sheet cannot be reopened. | UC-33 | Reopening is deliberate and explained. | Dentist, Clinic Owner; system |
| GBR-061 | **Delete a sheet opened by mistake**<br>A sheet can be deleted only while Open and empty: no plan items, no events after creation, no appointments, work, drafts, documents or money records. | UC-33 | Never delete clinical or financial history. | System validation |
| GBR-062 | **Cancel treatment sheet**<br>Cancelling a sheet requires a reason (max 1000), is recorded in the finance ledger and is refused while a PayOS QR of the sheet is not reconciled. | UC-33, UC-39 | Cancellation keeps money traceable. | Dentist, Clinic Owner; system |
| GBR-063 | **Paid lab order protection**<br>A lab order cannot be deleted once the patient has paid toward it, and its fee cannot be lowered below the amount already paid. | UC-35, UC-39 | Protect recorded payments. | System validation |
| GBR-064 | **Lab order status flow**<br>Not sent to Sent; Sent to Received or Rework; Received to Delivered or Rework; Delivered to Rework; Rework to Sent. Each move is logged (note max 300) and the delivery date is set on delivery. | UC-36 | Track lab work through a fixed process. | Clinic Assistant, Clinic Owner; system state check |
| GBR-065 | **Material usage**<br>Recorded material quantities must not exceed the stock on hand; stock can never become negative. | UC-37, UC-42 | Stock figures stay real. | System stock check |
| GBR-066 | **Prescription**<br>Only a dentist (or granted staff) of the branch prescribes: 1-30 medicines, quantity 1-10,000, unit max 40, instructions max 1000, date not in the future, a prescribing dentist of the branch, and a non-archived patient. Edits check the version. | UC-38 | Prescriptions are issued by authorized dentists. | Dentist; system validation |
| GBR-067 | **Payment authority**<br>Only the Clinic Owner records payments, advances, allocations and forfeits and views finance figures. | UC-39, UC-45 | Restrict money handling to one accountable role. | System permission check |
| GBR-068 | **Payment amounts**<br>The payment date cannot be in the future; each line is at most the remaining due; the total is at most 1,000,000,000,000 VND. A request key prevents recording the same payment twice. | UC-39 | No overpayment or duplicate receipts. | Clinic Owner; system validation |
| GBR-069 | **Lab fee priority**<br>Before collecting other services of a sheet, at least 30% of each lab fee must be paid; a lab allocation cannot exceed the lab amount due. An advance is applied first to that lab priority. | UC-39, UC-35 | The clinic covers its lab cost first. | System payment validation |
| GBR-070 | **Advance allocation**<br>The amount allocated from an advance cannot exceed the advance balance, and each line cannot exceed its amount due. | UC-39 | Allocations match money actually received. | Clinic Owner; system validation |
| GBR-071 | **Forfeit advance of a no-show**<br>An advance can be forfeited only for an Open sheet that has an advance balance, no treatment work or lab order, no other money transaction and no unreconciled QR; a reason is required. | UC-39, UC-18 | Forfeit only money that was never used. | Clinic Owner; system validation |
| GBR-072 | **PayOS QR payment**<br>A QR order is created only when PayOS is configured, with an amount above 0; one active QR per sheet and purpose, valid 30 minutes. Payment is confirmed only from a signed webhook or the reconcile job that runs every 15 seconds. | UC-39 | Online payments are confirmed from a trusted source. | System PayOS integration |
| GBR-073 | **Deactivate instead of delete**<br>Entries already used are deactivated, not deleted; deactivating or reactivating needs a reason (max 500); reserved system entries cannot be deactivated; inactive entries cannot be chosen for new transactions; a material category that still has items cannot be deleted. | UC-40, UC-41 | Keep history referring to valid catalog data. | Clinic Owner; system validation |
| GBR-074 | **Unit conversion**<br>Conversion to the base unit is exact and never rounded: materials allow at most 3 decimal places, medicines must convert to whole base units. | UC-37, UC-38, UC-41, UC-42 | Stock and doses stay exact. | System unit conversion |
| GBR-075 | **Stock balance**<br>Stock on hand = quantity received - quantity used; editing a purchase cannot make the stock negative. | UC-42, UC-37 | Stock never shows impossible values. | System stock calculation |
| GBR-076 | **Deactivate a branch**<br>A branch cannot be deactivated while it has future appointments not cancelled, waiting or ongoing visits, open treatment sheets or lab orders not delivered. The impact is previewed, a reason is required and nothing is cancelled automatically. | UC-43 | Do not abandon patients' open obligations. | Clinic Owner; system impact check |
| GBR-077 | **Chair status**<br>A chair can be activated only when its branch is active, and cannot be deactivated while it still has the obligations shown in the impact preview. | UC-43 | Booked chairs stay available. | Clinic Owner; system impact check |
| GBR-078 | **General settings versions**<br>Each save creates a new version with a reason (max 500); restoring an older version creates a new version; saving without changes is refused; a concurrent edit is detected. The code prefix uses up to 12 uppercase letters, digits or hyphens. Changes apply only to new records and the next print. | UC-44 | Settings changes are traceable and reversible. | Clinic Owner; system versioning |
| GBR-079 | **Concurrent updates**<br>Every update carries the version the user last saw; if the data changed in between, the update is refused and the user reloads. | All | Never overwrite another user's change. | System version check |
| GBR-080 | **Repeated commands**<br>Each command carries a request key; repeating it returns the original result and reusing the key for different content is refused. | All | A double click or retry never duplicates data. | System request receipts |
